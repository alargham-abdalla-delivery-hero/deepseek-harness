## Context

Model output today is text/markdown content blocks. The proposal wires in [OpenUI](https://github.com/thesysdev/openui) — an MIT-licensed, self-hosted generative-UI framework: a fixed component vocabulary (Zod schemas), a compact DSL ("OpenUI Lang") the model emits instead of prose, a parser that turns that DSL into a typed element tree, and a React renderer that draws it. The harness has two extension points that already fit this without touching shared infrastructure:

- A model-facing **tool** (`packages/core/tools`) with `execute` (canonical JSON in/out) and `presentCall`/`presentResult` (pure render-intent projections, replay-safe).
- A web-client **keyed `tool.call.toolview` slot** (`packages/client/ui-tool/src/client/contract/slots.ts`): any plugin may register a component under `key: '<tool name>'` to fully own that tool's chat-turn rendering; an unclaimed key falls back to the generic card. `web-row.tsx` (`webToolview`) is the reference registrant.

This design treats OpenUI as a **new tool + a new keyed client renderer**, not a change to the six-member `card` union in `packages/core/tools/src/presentation.ts`. That union is the neutral vocabulary every host (web, CLI, ACP) must map — extending it would force every non-web host to grow an opinion about arbitrary generative UI it cannot render. The keyed slot is scoped to the one host (web) that can actually draw React components.

## Goals / Non-Goals

**Goals:**
- Let the model produce rich, interactive UI (cards, tables, charts) in the web chat client via a documented extension point, with zero new hosted dependency.
- Keep the taught grammar (system prompt), the server-side validator, and the client's renderable component set as one source of truth, so they cannot silently drift apart.
- Fail safe on malformed model output: a syntax/schema error is a domain outcome the model can read and retry, not a crash.
- Give non-web hosts (CLI, ACP) a useful fallback instead of a broken or empty card.

**Non-Goals:**
- Rendering arbitrary model-authored HTML/JS. The component vocabulary is closed and server-validated; no "raw HTML" or "raw script" component is in scope, ever.
- A pluggable/swappable "provider" model for the component library (multiple competing vocabularies). There is exactly one current consumer and no evidence today of a second, so this ships as a fixed shared definition, not a capability seam with Service Definition/Provider roles.
- ~~Making the tool default-on in every bundle.~~ **Superseded** (see Migration Plan): shipped opt-in first for the prompt-token-cost/new-dependency reasons stated here, then made default in `packages/bundle/base`/`packages/bundle/web-app` on explicit request.
- Streaming partial OpenUI Lang mid-generation into a live-updating card. First cut renders only after the tool call settles (the existing pending/settled pattern every other card follows).
- **Wiring OpenUI's `Query()`/`Mutation()`/`$variables`/`ToolProvider` reactive layer.** OpenUI Lang is not only a display format — its runtime (`createQueryManager`, `evaluate`, `ToolProvider`, `extractToolResult`) lets a rendered component call back into tools and hold live state. v1 uses OpenUI purely as a one-shot rendering format for an already-complete, already-settled tool result: no `ToolProvider` is wired up, no component in the curated set declares a `Query`/`Mutation`, and the rendered UI never triggers a new tool execution on its own. Letting model-authored UI call arbitrary tools outside the normal model-loop-mediated flow is a distinct, larger security surface than this change covers.

## Decisions

**1. New group `packages/openui/`, split into a shared spec package and a tool package, plus a client package under `packages/client/`.**

Verified against the installed `@openuidev/lang-core@0.2.15` type declarations: `defineComponent<T, C>({ name, props: ZodObject, description, component: C })` and `createLibrary<C>({ components, root? })` live in framework-agnostic `lang-core` itself (not React-only) and are generic over the renderer payload `C`, which "lang-core never inspects — it is stored opaquely and consumed by the framework adapter's Renderer." `@openuidev/react-lang` re-exports the identical functions specialized to `C = ComponentRenderer<any>` (a React component). This means one shared list of `{ name, props, description }` component specs can construct **two** `Library` instances — a server one with `component: undefined` and a client one with the real React function per name — without either side re-deriving the other's schema:

- `packages/openui/openui-lang` (`@deepseek-ai/dsh-openui-lang`): framework-agnostic, imports `defineComponent`/`createLibrary`/`createParser`/`ParseResult`/`Library` directly from `@openuidev/lang-core` (no React). Exports the shared component spec array (`name`, Zod `props`, `description` — no `component` value) plus a `buildServerLibrary()` helper that calls `defineComponent({ ...spec, component: undefined })` for each and `createLibrary({ components })`. Exposes `library.prompt(options)` (grammar/vocabulary text for the system prompt) and `createParser(library.toJSONSchema()).parse(source): ParseResult` for validation.
- `packages/openui/tool-openui` (`@deepseek-ai/dsh-tool-openui`): registers the `render_ui` tool and a `ctx.systemPrompt.section()` built from `openui-lang`'s `library.prompt()` output (tool-guidance band, order 100–199, per `docs/cookbook/adding-a-tool.md` convention). Depends on `dsh-openui-lang`, `dsh-tools`, `dsh-system-prompt`.
- `packages/client/ui-openui` (`@deepseek-ai/dsh-client-ui-openui`): registers a `tool.call.toolview` keyed to `render_ui` (same pattern as `webToolview` in `ui-tool`). Imports the same component spec array from `dsh-openui-lang`, supplies the real React `component` per name, builds its own client `Library` via `@openuidev/react-lang`'s `createLibrary`, and renders the settled result's persisted `root` element tree. Depends on `dsh-openui-lang`, `dsh-client-ui-slots`, `@openuidev/react-lang`.

One shared spec array, two `Library` instances (Node tool, browser renderer) — this is the "symmetry for parallel values" the repo conventions call for; duplicating the component list in both places is the asymmetry to avoid.

**2. Tool output mirrors OpenUI's own lenient `ParseResult`, not an invented pass/fail union.**
`createParser(...).parse(source)` always returns `{ root: ElementNode | null, meta: { incomplete, errors: ValidationError[], unresolved, orphaned, statementCount }, stateDeclarations, queryStatements, mutationStatements }` — parsing is lenient: a component with an invalid or unknown reference (`ValidationErrorCode` includes `"unknown-component"`, `"missing-required"`, `"type-mismatch"`, etc.) is dropped from the tree and recorded in `meta.errors` with an already-humanized `message`, rather than failing the whole parse. `render_ui`'s canonical output value is exactly this shape (trimmed to `root`, `errors`, `incomplete`) rather than an invented `{ok, tree}` union — `execute()` never throws for malformed or partially-invalid OpenUI Lang, since that is the model's own recoverable output (same reasoning `docs/cookbook/adding-a-tool.md` gives for a non-zero shell exit code: "Represent a successful domain outcome... even when its Native renderer explains a non-ideal state"). `output.render()` echoes a short confirmation when `root` is non-null and `errors` is empty, otherwise the humanized error messages, so the model can self-correct on the next turn. `execute()` still throws only for a genuine infrastructure failure (the parser implementation itself crashing) — that stays `isError`.

**3. Server-side parse/validate is mandatory before the client ever sees a tree.**
The raw OpenUI Lang string is untrusted model output — a model/tool-JSON boundary per repo convention, so it gets validated, not trusted. The server parses it with `dsh-openui-lang`'s server `Library.toJSONSchema()` + `createParser()`; the client never re-parses raw text.

**4. The element tree reaches the client through `output.presentationMeta`, not a new wire field.**
Verified against the actual wire path (`packages/core/session/src/types.ts`'s `tool/result` event carries `meta?: JsonValue` → `packages/host/apiproxy`'s `session/event` frame ships the event verbatim → `packages/client/ui-conversation/src/client/conversation-nodes/tool.ts:66` reads it straight into `ToolResultNode.meta: unknown`): the wire does NOT carry a tool's raw `execute()` return value to the client at all — only `content`, `callView`/`resultView` (the closed card union), and whatever `output.presentationMeta(args, value)` projected into `meta`. Since `render_ui`'s canonical value already IS `{ root, errors, incomplete }` with no richer result-time derivation needed, `presentationMeta` is the identity function `(_args, value) => value`. `presentCall`/`presentResult` stay pure and card-`generic`:
- `presentCall`: `{ card: 'generic', title: 'Render UI', kind: 'other' }` (pending; no tree exists yet).
- `presentResult`: `{ card: 'generic', title: 'Render UI' }` on success (content omitted — the generic card's fallback already renders `output.render()`'s text); `undefined` on `isError` (a genuine parser crash, not a validation issue) so the default generic error rendering applies. This is what CLI and ACP hosts show — a plain but honest fallback, never a broken card.
- The web client's `ui-openui` toolview reads `(block as ToolResultNode).meta` — the exact same JSON `execute()` returned, round-tripped through the durable log — and renders it through `@openuidev/react-lang` instead of using the generic card. Pure function of the settled result's `meta` — replay-safe by construction, since `meta` is itself durable/logged.

**5. Author a small custom component set; do not depend on a third-party prebuilt library for v1.**
Neither `@openuidev/lang-core` nor `@openuidev/react-lang` ships any built-in components — every component is author-defined via `defineComponent`, there is no built-in `openuiChatLibrary`/`openuiLibrary` in this dependency (an earlier, unverified secondary source claimed otherwise; verified false against the installed package's exports). Thesys does publish a separate prebuilt package, `@openuidev/react-ui`, but pulling in a second third-party component implementation for a security-relevant rendering surface without reviewing its source is out of scope for v1. Ship a small, explicitly reviewed, hand-authored set (e.g., heading/text/card/table/list — no component whose props accept a URL, raw markup, or arbitrary script) directly in `dsh-openui-lang`/`dsh-client-ui-openui`. Expand only against an evidenced need, per the repo's "require evidence for public choices" convention.

## Risks / Trade-offs

- **[Risk] A third-party React renderer becomes an XSS vector if any bundled component accepts raw HTML/markup or uses `dangerouslySetInnerHTML`/`eval`/`new Function`.** → Mitigation: hand-authored curated component subset (Decision 5); a `grep` of the installed `@openuidev/lang-core@0.2.15` and `@openuidev/react-lang` compiled `dist/` output found no `dangerouslySetInnerHTML`, `eval(`, or `new Function(` in either package as of this check — re-run this grep against the exact versions pinned at implementation time, since it is a point-in-time result, not a permanent guarantee across upstream updates.
- **[Risk] `@openuidev/lang-core` sends pseudonymous installation telemetry to PostHog by default** during `npm`/`pnpm install` (a random install ID, a salted-hash project identifier, and Lang Core/Node/OS/package-manager versions — no source code, prompts, paths, or repository URLs per its documented disclosure). This is a real difference from the proposal's "no new external network egress" framing: it is install-time-only (no default runtime network calls; the separate opt-in runtime telemetry stays off unless `OPENUI_RUNTIME_TELEMETRY_ENABLED=1` is set), but it is still an undisclosed-by-default egress from any machine that runs `pnpm install` with this dependency present. → Mitigation: set `OPENUI_TELEMETRY_DISABLED=1` (or rely on `DO_NOT_TRACK=1` if already set) in this repo's install environment/CI for any package depending on `@openuidev/lang-core`, and disclose this in `dsh-openui-lang`'s README per the repo's Model Experience / dependency-disclosure conventions. This is a decision for whoever owns dependency/security sign-off, not something to silently accept.
- **[Risk] System-prompt token cost grows for every session that enables this tool** (grammar + component signatures via `library.prompt()`). → Mitigation: opt-in bundle (Open Question 4), curated component subset keeps the generated prompt small.
- **[Risk] Non-web hosts (CLI/ACP) get materially less value** (a generic card, not the rich UI) since there is no React renderer there. → Accepted: this is inherent to a browser-only rendering technology; the fallback still exposes the model's structured output as readable text/errors.
- **[Trade-off] No mid-stream partial rendering, and no `Query()`/`Mutation()`/`ToolProvider` wiring (Non-Goals).** Simpler, replay-safe, consistent with every other card kind's pending/settled split, and avoids a second, much larger security surface (model-authored UI calling tools on its own). Revisit only against explicit product demand for either.
- **[Resolved during implementation] The client component map's exhaustiveness check needs no runtime call.** An earlier revision of `dsh-client-ui-openui` called `dsh-openui-lang`'s `buildLibrary(COMPONENTS)` at module scope purely to force the same "every curated name needs a value" check the `ClientComponentMap` (= `ComponentRenderers<OpenUIComponent>`) type annotation on `COMPONENTS` already provides for free at compile time. That runtime call pulled `@openuidev/lang-core`'s full module (parser, prompt generation, and its install-time-telemetry-adjacent `ci-info` dependency) into the browser bundle for zero behavioral benefit — confirmed by an actual `tsdown --env.DSH_BUILD_FACE client` build: 238.65 kB before, 8.50 kB after removing the call and keeping only `dsh-openui-lang`'s type imports (erased at compile time, so `@openuidev/lang-core` never reaches the browser artifact at all).

## Migration Plan

Purely additive: new packages, one new tool, one new client plugin, no changes to `SESSION_FORMAT_VERSION`, the wire protocol, or any existing tool/card. Nothing depends on this tool's result schema outside its own client renderer, so it carries no compatibility promise beyond normal semver.

- **Rollout**: shipped opt-in first, via an example/demo overlay, so adoption was a deliberate `cordis.yml` inclusion. **Superseded**: on explicit request, `tool-openui` was registered in `packages/bundle/base` and `ui-openui` in `packages/bundle/web-app`, making `render_ui` default in every profile built on those bundles; the demo overlay was removed as redundant. Open Question 4 is resolved by this: no separate preset-owner opt-in decision remains outstanding.
- **Rollback**: remove the `tool-openui`/`ui-openui` rows from `packages/bundle/base`/`packages/bundle/web-app` (and their `package.json` dependencies); no data migration needed since no other capability reads `render_ui`'s result shape.
