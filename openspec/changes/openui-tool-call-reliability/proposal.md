## Why

`openui-generative-output` (`openspec/changes/openui-generative-output`) wired the `render_ui` tool and the web client's keyed renderer, but only covers the case where the model actually issues a `render_ui` tool call — the client reads the parsed tree from that call's persisted result and never re-parses raw text (a deliberate security decision: server validates, client only renders an already-validated tree). Observed in practice: the model instead writes OpenUI Lang source (e.g. `root = Stack([...])`, `header = Card([...], "Sales Dashboard")`, …) directly as plain assistant chat text, with no `render_ui` tool call at all. Nothing in the current pipeline reacts to that — the chat client shows the literal OpenUI Lang source as an ordinary markdown message instead of a table/chart. This is plausible model behavior independent of this harness's tooling: OpenUI/Thesys is public, so the base model can reproduce its DSL syntax from pretraining without ever having been taught to route it through this repo's `render_ui` tool.

The fix stays a prompting/self-correction problem, not a rendering-architecture problem — but the diagnosis is more direct than "missing guidance." Calling `promptText()` (the exact call `tool-openui/src/index.ts:63` makes today, with no options) and reading its actual output shows the generated `tool:render_ui` system-prompt section *opens* with `@openuidev/lang-core`'s built-in default preamble: "You are an AI assistant that responds using openui-lang... **Your ENTIRE response must be valid openui-lang code — no markdown, no explanations, just openui-lang.**" That text is written for OpenUI/Thesys's own raw-completion architecture, where the model's entire reply IS the DSL with no wrapping tool call — it directly instructs the model, in its own system prompt, to do exactly the thing this change exists to stop. This is very likely the primary, direct cause of the observed behavior. Two further facts round out the fix: this repo's LLM abstraction has no `tool_choice`/forced-tool-use field at all (`GenerateOptions` in `packages/llm/llm/src/types.ts` documents sampling as `temperature`/`maxTokens`/`stop` only — see `packages/llm/llm/README.md` and the archived `drop-inert-request-knobs` Agent Note — so there is no request-layer knob to force this specific tool call even if one were wanted); and once the preamble stops contradicting tool use, the prompt still only teaches grammar, not usage, with no worked example of the tool being called correctly. As a backstop beyond prompting, the agent loop provides `agent/turn-stopping`, a serial hook fired after a turn's `step()` completes and before turn close, already used by `hooks-claude-code`/`hooks-codex` to call `agent.steer(...)` and force another step when a turn's output fails some check — the same shape of self-correction this needs for any residual case: detect a turn whose assistant text parses as real OpenUI Lang with no accompanying `render_ui` call, and steer the model to resend it as a proper tool call before the turn's answer is considered final.

## What Changes

- `dsh-tool-openui` overrides `@openuidev/lang-core`'s default `preamble` via `dsh-openui-lang`'s `promptText(options)`, so the `tool:render_ui` system-prompt section tells the model OpenUI Lang is sent only as the `render_ui` tool's `source` argument, never as the direct chat reply — replacing the shipped default text that currently says the opposite.
- `dsh-tool-openui` also passes a concrete worked example (an OpenUI Lang source string demonstrating a `render_ui("...")`-shaped call, e.g. a small `Stack`/`Card`/`Text` tree) through the same `promptText(options)` call, so the system prompt shows what calling the tool correctly looks like, not only its grammar and component signatures.
- `dsh-tool-openui` registers a listener on `agent/turn-stopping` that, once per completed turn, inspects that turn's assistant message content (via `agent.session.deriveMessages()`) for a text block whose content parses via `dsh-openui-lang`'s existing `parseSource()` to a non-null root with no validation errors, where that same assistant message contains no `render_ui` tool call. On a match, the listener calls `agent.steer(...)` with a corrective instruction telling the model to resend that exact content as a `render_ui` tool call instead of prose, forcing another step.
- The correction is capped per turn (a bounded number of consecutive re-prompts before giving up and letting the prose stand) so a model that keeps refusing to call the tool cannot loop indefinitely — this change must implement that cap itself, not merely note it as a known gap.
- No change to `dsh-openui-lang`'s parser/vocabulary, `dsh-client-ui-openui`'s renderer, the `render_ui` tool's schema, the wire protocol, or `SESSION_FORMAT_VERSION`. The client still never re-parses raw text; detection and correction both happen server-side, and the model's corrected turn still goes through the same validated `render_ui` call path as today.

## Capabilities

### New Capabilities
(none)

### Modified Capabilities
- `openui-render-tool`: replaces the misdirecting default system-prompt preamble with one that correctly scopes OpenUI Lang to the tool argument, adds a worked usage example to the system-prompt contribution, and adds a turn-completion self-correction requirement so a model that writes OpenUI Lang as plain text instead of calling the tool is steered to retry via the tool, bounded by a per-turn cap. All three additions ship inside the existing `dsh-tool-openui` plugin (`packages/openui/tool-openui`) — this change introduces no new plugin package.

## Impact

- **Affected package**: `packages/openui/tool-openui` only (`dsh-tool-openui`) — adds an `agent/turn-stopping` listener and an options argument to its existing `promptText()` call. `packages/openui/openui-lang` (`dsh-openui-lang`) is a consumer, not a change: its already-shipped `parseSource()` is reused as-is for detection, with no new parsing logic.
- **New dependency**: `dsh-tool-openui` gains `inject: ['agent']` (or the equivalent context capability exposing `agent/turn-stopping` and `agent.steer`) alongside its existing `tools`/`systemPrompt` injections.
- **Token/prompt cost**: the worked example adds a small, fixed amount of system-prompt text, proportional to one example tree (not to the curated component count) — same amortization as the rest of `promptText()`'s output.
- **Behavioral risk**: an incorrectly-tuned detector (e.g. one that fires on legitimate prose that merely resembles the DSL) would inject spurious correction turns; the detector's use of the real `parseSource()` validator (not a regex heuristic) and a requirement that the parse succeed with zero errors bounds this, but is not a formal proof against a false positive — see design.md Risks.
- **No changes** to the client renderer, the tool's result schema, the wire protocol, or any other tool's behavior.
