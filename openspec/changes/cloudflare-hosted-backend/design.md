## Context

Today a Workspace is a Cordis-plugin entity (`@deepseek-ai/dsh-workspace`, `ctx.workspaceRegistry`) persisted through the generic `ctx.storageDomain` seam (`packages/storage/`) to local JSON or SQLite, and exposed to Clients as `ctx.remote.workspace` by `packages/api/workspace-controller` over the Typert API Gateway. Session message/event history is a separate seam (`packages/session/`) with its own SQLite (`SCHEMA_VERSION`) and JSONL (`SESSION_FORMAT_VERSION`) backends. `apps/web`'s static bundle cannot boot standalone — `apps/web/vite.config.ts`'s `rejectStandaloneServe` plugin enforces that only a Node host (`apps/cli`'s `dsh web`, via `packages/host` and `packages/boot`) can inject `window.__DSH_BOOT__` and back the RPC/session/workspace state. `packages/e2b` is the closest existing precedent for a remote-runtime provider (a Service Provider that runs tool execution somewhere other than the local machine), though it targets E2B's sandbox product, not Cloudflare. Confirmed via the `cloudflare` skill: Cloudflare Containers (beta) run a Container as a Durable Object with persistent identity (`getByName(id)`), support arbitrary Node.js/subprocess/filesystem workloads, but the container's disk is ephemeral — it resets on stop — so anything that must survive a restart has to live in D1 or Durable Object storage instead.

**Implementation update (`dsh-storage-d1`, built and verified):** D1 also has a documented REST query API (`/accounts/:id/d1/database/:id/query`, "server-side scripts" / "non-Worker integrations") reachable with plain `fetch` plus an account id, database id, and API token — no Workers/Durable Object binding required. `dsh-storage-d1` uses this path, which simplifies the architecture below it: the D1-backed storage and session-persistence providers run as ordinary Node code inside the Container (or anywhere else) and talk to D1 directly, with no need for the Container to proxy persistence calls back through its owning Durable Object's binding. The binding-based access model remains relevant only for the edge-gateway Worker and host-container Durable Object themselves (sections 5-6 of tasks.md), not for reaching D1.

## Goals / Non-Goals

**Goals:**
- A Workspace created against the Cloudflare backend is durably registered in D1, its Sessions' event history is durably persisted in D1, and both reload correctly after the owning container stops and restarts.
- `apps/web` can talk to a deployed Cloudflare backend as a drop-in alternative to a local `dsh web` process, with no change to its Remote call surface.
- The real dsh Host process runs per Workspace, with full subprocess/filesystem/lsp tool capability, inside the Container's own disk.
- A real, working deployment to the user's own Cloudflare account, gated so it is not open to the public internet.

**Non-Goals:**
- Multi-tenant account system (sign-up, per-end-user billing, cross-account sharing). This proposal targets a single owner deploying their own hosted instance, gated by Cloudflare Access — the same pattern this repo already uses for PR-preview hosting (`.agents/notes/implemented/architecture/2026-08-20-preview-cloudflare-pages-deploy.md`). A multi-tenant identity system is a separate, later proposal if the need arises.
- Making cloud-hosted tool capability reach the end user's real local machine. A cloud-hosted Workspace's filesystem is the container's own disk, full stop (see `cloudflare/host-container` spec).
- Migrating existing local Workspaces/Sessions into Cloudflare. This proposal adds a new deployment target; it does not touch the local `dsh web` path or write an import tool.
- Autoscaling or multi-region active-active routing beyond what `getByName(workspaceId)` gives by construction (session affinity to one Durable Object).

## Decisions

**Container granularity: one Container per Workspace, not per Session.** A Workspace already scopes one or more Sessions to one working directory locally; a Workspace-scoped container preserves that grouping and lets Sessions in the same Workspace share filesystem state, matching today's local behavior where multiple Sessions run against the same project directory. Alternative considered: one container per Session — rejected because Sessions in a Workspace need to see each other's files today (e.g. one Session's edit is visible to another opened later in the same Workspace); per-Session containers would silently break that.

**Package placement follows the existing group conventions, not a single new mega-package.** `packages/storage/` and `packages/session/` groups explicitly document themselves as "seam + backends" and "persistence seam + backends" — a D1-backed provider joins each as a sibling to the existing `dsh-storage-sqlite`/`dsh-storage-json` and `dsh-session-persistence-sqlite`/`dsh-session-persistence-jsonl` packages, with **no change** to either Service Definition. The Worker/Container orchestration has no existing owner (closest precedent is `packages/e2b`, but that targets E2B's own product) and becomes a new group, `packages/cloudflare/`, holding the edge-gateway Worker and the Container-hosting Durable Object.

**Revised during implementation: one package, not two.** `packages/cloudflare/cloudflare-worker` (`@deepseek-ai/dsh-cloudflare-worker`) holds both the edge-gateway Worker entrypoint (`src/gateway.ts`) and the Container-backed Durable Object (`src/host-container.ts`) as one deployable `wrangler.jsonc` unit, rather than tasks.md's original two-package split (`cloudflare-host-container` / `cloudflare-edge-gateway`). Both halves are compiled and deployed together by the same `wrangler deploy` regardless of package boundaries — they are never independently versioned, independently deployed, or consumed by a different caller (the gateway is `HOST_CONTAINER`'s only caller; the Durable Object is meaningless without the gateway routing to it) — so a package split would add cross-package import overhead without a real seam to protect, unlike the storage/session split where each side has its own independent consumer (`dsh-workspace` vs. `dsh-session`). This keeps the "join an existing group unless the family is genuinely new" rule from `packages/README.md`, and `packages/cloudflare/README.md` documents the one package this group currently holds.

**The whole capability ships as one new, opt-in profile bundle — a plugin, not a modification.** `packages/bundle/` is exactly the existing extension point for this: each package there declares `dsh.bundle.patch`, and the launcher stacks those patch documents into a named `dsh --profile` (`dsh-web-app` → `dsh --profile web` is the direct precedent). This proposal adds `packages/bundle/cloudflare-app` (`@deepseek-ai/dsh-cloudflare-app`), patching over `dsh-base` exactly as `dsh-web-app` does, and composing the four capabilities above (`dsh-storage-d1`, `dsh-session-persistence-d1`, the edge-gateway Worker, the host-container Durable Object) into one selectable profile — or an out-of-tree add-on via `dsh plugin --profile <name> add @deepseek-ai/dsh-cloudflare-app`, per the existing bundle mechanism. Every plugin the bundle mounts registers only through `ctx.effect()`/`ctx.on()` (this repo's "registrations are effects" rule), so the entire capability is fully present or fully absent — there is no code path where enabling Cloudflare support alters the default `web`/`headless`/`acp`/`sdk` profiles' behavior, and no in-place edit to `dsh-base` or any existing bundle package. Alternative considered: wiring the D1 providers and Worker/Container plugins directly into `dsh-base` or `dsh-web-app` behind a config flag — rejected because it would make every default profile carry Cloudflare-specific code paths and dependencies (`@cloudflare/containers`, `wrangler` types) it never uses, and would violate "no hardcoded tunables in plugins" by needing a flag to turn behavior off rather than simply not mounting it.

**Two-tier storage: D1 for durability, Durable Object SQLite storage reserved but currently unused.** The Workspace registry and session event log live in D1 because they must be readable and listable even while a Workspace's container is stopped (e.g. listing Workspaces in the sidebar must not require waking every container). The Container-backed Durable Object's own SQLite storage (`this.ctx.storage`, enabled via `new_sqlite_classes` migration in `wrangler.jsonc`) is provisioned for future in-memory-equivalent coordination state, but **revised during implementation: the Worker/Durable-Object layer holds none today.** `host-container.ts`'s `HostContainer.fetch()` is a pure pass-through — `@cloudflare/containers`' `Container.fetch()`/`startAndWaitForPorts()` proxies the raw request (including any WebSocket upgrade) directly to the container's own HTTP port; the `follow()` stream's generation/baseline bookkeeping lives entirely inside the `dsh` Host process running in the container, exactly as it does for a local `dsh web` process today, with no separate copy or cache at the Durable Object layer to lose or rebuild. The `new_sqlite_classes` migration stays in place (Durable Objects cannot add SQLite storage retroactively without a migration, and removing an already-shipped migration is not reversible) so a future need — e.g. the gateway itself terminating WebSocket Hibernation instead of just proxying — has it available without another migration.

**New, independent D1 schema version, not a shared lineage with the local SQLite schema.** The D1 provider defines its own version marker (e.g. `D1_SCHEMA_VERSION` starting at `1`) rather than continuing `SESSION_PERSISTENCE_SQLITE`'s `SCHEMA_VERSION = 19` — the two backends store the same logical data but are independent on-disk/on-D1 formats with independent migration lifecycles, consistent with this repo's pre-release "no compatibility shims" stance applying per-backend, not repo-wide.

**Auth: Cloudflare Access in front of the Worker, not an in-app login system.** Reuses the exact pattern already proven in this repo for the PR-preview deployment, rather than building new account/session/credential UI. **Revised during implementation:** since this proposal explicitly excludes multi-tenancy (Non-Goals above) and `dsh-workspace`'s `WorkspaceRecord` carries no owner/account field, "the caller owns the Workspace it names" resolves to "Access already restricted the whole Worker to its one authorized principal or allowlist" — there is exactly one tenant per deployment, so per-Workspace ownership and deployment-wide authentication collapse to the same check. The edge-gateway Worker's own step beyond Access is a Workspace-existence check against the D1-backed registry (reject an id with no matching record) rather than an owner-identity comparison — this still prevents routing to (and billably waking a container for) a nonsense or stale Workspace id, without inventing an owner field this proposal does not otherwise need. Real per-Workspace, per-user ownership is deferred to the later multi-tenant proposal Non-Goals already calls out.

**Container image ships the already-built `dsh` Host, not a source checkout.** The Dockerfile installs Node and copies `apps/cli/lib` (the built output already used by the local path today) plus a new boot profile analogous to `dsh web`, so the container runs the identical Host code path this repo already tests locally — the only new code is the edge-gateway/Container-DO orchestration layer, not a second implementation of the Host.

## Risks / Trade-offs

- [Cloudflare Containers is beta, no SLA, API can change without notice] → Pin the `@cloudflare/containers` and `wrangler` versions used; treat container-orchestration code as the most likely place to need follow-up changes, and say so in the Agent Note this change ships with.
- [Container cold start (2-3s) on every wake from idle] → Surfaced explicitly to the caller as a distinct "starting" status (per `cloudflare/edge-gateway` spec) rather than hidden latency; acceptable for a personal/low-traffic deployment, revisit `sleepAfter` tuning if it proves disruptive.
- [D1 is the durability floor — a D1 outage or throttling makes Workspaces unreadable even though containers may be healthy] → No in-repo mitigation proposed beyond surfacing D1 failures as explicit `WorkspaceError`s (per spec); Cloudflare's own D1 availability is an accepted dependency, same as any hosted database choice.
- [Concurrent-write correctness on D1 is new terrain for this codebase — no existing package does optimistic-concurrency-style writes against a remote SQL database] → Addressed as an explicit spec requirement (`cloudflare/workspace-persistence` concurrent-mutation scenarios) so it is tested, not assumed.
- [Real deployment creates real, billed Cloudflare resources] → tasks.md sequences an explicit "confirm Cloudflare account and budget expectations with the user" step before the first resource-creating command, and every subsequent `wrangler` command that creates or costs money is called out individually rather than bundled into a single opaque "deploy everything" script.

## Migration Plan

1. Build the four new packages (`dsh-storage-d1`, `dsh-session-persistence-d1` as new backends in their existing groups; `dsh-cloudflare-edge-gateway`, `dsh-cloudflare-host-container` as the new `packages/cloudflare/` group) and verify each against its spec with unit/integration tests using Miniflare's local D1/Durable Object emulation — no live Cloudflare account needed yet.
2. Build the Container image and verify `wrangler dev` boots the Host inside a local container emulation, reachable from a local `apps/web` build, end to end.
3. Obtain the user's Cloudflare account access (API token or `wrangler login`) as an explicit, separate step — do not assume it is already available.
4. Create the real D1 database and apply the D1 schema migration.
5. Deploy the Worker and Container image to the real account behind Cloudflare Access.
6. Verify end-to-end against the live deployment: create a Workspace from a browser pointed at the deployed URL, run a Session with a tool call, confirm the Workspace and its Session history reload correctly after the container has been allowed to idle out and restart.

**Rollback:** the Worker, Container, and D1 database are new resources with no existing traffic depending on them; rollback is deleting the Worker/D1 resources or leaving them deployed but unused, since the existing local `dsh web` path is completely unaffected either way.

## Open Questions

- Exact `sleepAfter` duration and container `instance_type` (cost/latency trade-off) — tunable after real-world usage, doesn't change the spec or task breakdown.
- Whether Session-history reads for a stopped Workspace should read directly from D1 without waking the container (fast path) or always wake the container first (simpler, one code path) — an implementation choice inside the `cloudflare/edge-gateway` and `cloudflare/host-container` capabilities, doesn't change their observable contracts either way.
