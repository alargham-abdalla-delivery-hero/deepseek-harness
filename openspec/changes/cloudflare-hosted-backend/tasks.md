## 3. `dsh-session-persistence-d1` (new backend in the `session/` group)

Revised during implementation, after reading `@deepseek-ai/dsh-session-persistence`'s `PersistenceCoordinator`: a backend implements only the much smaller `PersistenceBackend<TornMarker>` interface (loadStored/readStoredRevision/appendBatch/commitRepair/list, plus optional loadStoredFrom/materializeHeader/locate/close) — the coordinator supplies all revision tracking, write-behind batching, prepare/inspect/HMR-adoption, and crash-repair orchestration generically, exactly as `storage-domain`'s `DomainFacility` does for KV backends. This package also intentionally simplifies the physical layout versus `session-persistence-sqlite`: one row per event (no chunk-packing/zstd compression) and the SessionId used directly as the event table's foreign key (no internal integer surrogate key) — documented as deliberate scope decisions, not oversights, in the README's Known Limitations.

- [x] 3.1 Scaffolded `packages/session/session-persistence-d1` (`@deepseek-ai/dsh-session-persistence-d1`) implementing `PersistenceBackend<number>` against `dsh-d1-client`, plus `D1SessionPersistence extends SessionPersistence` delegating every service method to one `PersistenceCoordinator` instance (mirrors `SqliteSessionPersistence`'s glue exactly, `static inject = ['sessions']` included).
- [x] 3.2 Implemented durable per-event writes (`appendBatch`, atomic materialize-plus-first-batch via one D1 batch call) and full-history reads (`loadStored`) against the D1 session tables (`d1_session_schema_version`, `sessions`, `events`), plus `readStoredRevision`/`loadStoredFrom`/`list`/`listSnapshots`/`materializeHeader`/`commitRepair`.
- [x] 3.3 Implemented the `d1_session_schema_version` compatibility check: refuses to load with a plain `Error` on an unrecognized version (mirrors the SQLite backend's own plain-`Error` convention for physical schema failures — `SessionPersistenceCorruptionError`/`SessionFormatUnsupportedError` are the coordinator's own vocabulary for logical failures, not this backend's to throw).

- [x] 3.5 Verified existing `packages/session` consumers require zero code changes: `D1SessionPersistence` only implements the same abstract `SessionPersistence` surface `SqliteSessionPersistence` does; the shared contract suite exercises it entirely through the public `@deepseek-ai/dsh-session`/`@deepseek-ai/dsh-session-persistence` seam.

Design correction recorded in the package's README (Known Limitations): D1's REST API has no cross-call transaction, so unlike the SQLite backend's `begin-immediate` file lock, this backend cannot guarantee cross-process write isolation for concurrent writers to the same session — accepted because the wider architecture runs exactly one Host process per Workspace. Also simplified versus the SQLite backend: one physical row per event (no chunk-packing/zstd compression), and the session id used directly as the event table's foreign key (no internal integer surrogate key) — both documented as deliberate scope decisions.
