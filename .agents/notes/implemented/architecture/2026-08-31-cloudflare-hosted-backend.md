# Agent Note: Cloudflare-hosted backend (Worker + Container + D1)

Status: implemented

English | [中文](2026-08-31-cloudflare-hosted-backend.zh.md)

## Problem

Every existing `dsh` profile runs the Host process on the operator's own machine: `dsh web`'s browser UI still needs a local Node process to inject `window.__DSH_BOOT__` and back the RPC/session/workspace state (`apps/web/vite.config.ts`'s `rejectStandaloneServe` enforces this). There was no way to reach a real `dsh` Host — full subprocess/filesystem/lsp tool capability, not a sandboxed subset — from a browser without the operator's own machine staying on and reachable. `packages/e2b` is the closest existing precedent for a remote-runtime provider, but it targets E2B's sandbox product specifically, not a general hosted deployment.

## Decision

**Architecture.** `packages/cloudflare/cloudflare-worker` (`@deepseek-ai/dsh-cloudflare-worker`) is one deployable `wrangler.jsonc` unit holding both halves of the edge layer: `src/gateway.ts` (the Worker entrypoint) and `src/host-container.ts` (a Container-backed Durable Object, `getContainer(env.HOST_CONTAINER, workspaceId)` giving one Container per Workspace with session affinity). The gateway checks for Cloudflare Access's `Cf-Access-Jwt-Assertion` header, then — only for an explicit `/w/<id>/` path, never for the `DEFAULT_WORKSPACE_ID` routing-slot fallback — a Workspace-existence read against the D1-backed registry, before routing to the Durable Object. `HostContainer.fetch()` is a pure pass-through: `@cloudflare/containers`' `startAndWaitForPorts()` proxies the raw request (WebSocket upgrades included) straight to the container's HTTP port; a caller sees a distinct `{"status":"starting"}` (202) during cold start and `{"status":"failed"}` (502) when the container could not start at all, never an indefinitely pending request. The container ships the already-built `apps/cli/lib` Host — the same code path the local `dsh web` path already tests — booted via `dsh --profile cloudflare`, a new opt-in bundle (`packages/bundle/cloudflare-app`, `@deepseek-ai/dsh-cloudflare-app`) that patches over `dsh-base` exactly as `dsh-web-app` does. `dsh-storage-d1` and `dsh-session-persistence-d1` (new sibling backends in their existing `packages/storage/`/`packages/session/` groups) and `dsh-credentials-d1` (a new sibling in `packages/credentials/`) reach D1 over its REST query API (`fetch` plus an account id, database id, and API token) — no Workers/Durable Object binding required, so these run as ordinary Node code inside the Container. The Workspace registry and session/credential state are D1-backed specifically because they must be readable while a Workspace's Container is stopped — listing Workspaces reads `ctx.workspaceRegistry.list()` against the D1-backed `storage-domain`, never waking any Container.

**Single-principal auth, not multi-tenancy.** Cloudflare Access gates the whole Worker to one authorized principal, the same pattern this repo already uses for PR-preview hosting. Since `dsh-workspace`'s `WorkspaceRecord` carries no owner field and this proposal excludes multi-tenancy, "the caller owns the Workspace it names" collapses to "Access already restricted the whole Worker" — there is exactly one tenant per deployment. The edge-gateway's step beyond Access is the Workspace-existence check described above, which exists to avoid billably waking a Container for a nonsense or stale Workspace id, not to compare ownership.

**Container-network and safety-guard reality, found only by deploying for real.** The container binds `0.0.0.0` (all interfaces) — `dsh-host-webserver`'s `Config.host` schema is a closed `'127.0.0.1' | '0.0.0.0'` union, so no other literal parses at all, and Cloudflare's own container port-health-check connects on an address this process cannot discover or bind individually. `dsh-web-app`'s CLI intentionally rejects the literal `--host 0.0.0.0` as a local-machine safety guard against exposing remote code execution to a LAN; `dsh-cloudflare-app`'s config patch sets the webserver row's `host` directly, bypassing the `--host` flag path (and its guard) rather than weakening it for the shared `dsh-web-app` surface, since this Container is reachable only through Cloudflare's own internal proxy. The same reasoning appears twice more, both new `ConnectionConfig` fields on `dsh-client-connection`, both false by default everywhere else: `requireBrowserSession` (dsh-web-app's own random per-process launch-token gate can never be satisfied here, since this profile disables both printing and opening the URL that would carry it) and `trustedAsHost` (`dsh-ui-settings`'s Models Settings UI refuses to persist through the Host for any non-loopback origin by default, a safety gate against an untrusted LAN caller). Both premises fail the same way: Cloudflare Access authenticates every caller before this container ever sees a request, so the origin being non-loopback no longer implies an untrusted caller. `dsh-cloudflare-app`'s deployment-declared hostname (`CLOUDFLARE_WORKER_HOSTNAME`, forwarded from the Durable Object's own binding into the container's environment the same way the D1 identity is) feeds the Host/Origin trust fence, which otherwise refuses every request whose `Host` is neither loopback nor an explicitly configured authority.

**D1 REST batch requests are `{"batch": [...]}`, not a bare array.** `D1Client.batch()` originally sent a bare JSON array for multi-statement calls; Cloudflare's REST API requires the array wrapped under a `batch` key (confirmed against the live API and against Cloudflare's current docs). Every multi-statement `ensureSchema()` call — `dsh-storage-d1`, `dsh-session-persistence-d1`, `dsh-credentials-d1` — was failing this way in the real deployment, and the same bug had also silently broken those three packages' own `fake-d1-server.ts` test doubles, so the bug shipped without a failing test to catch it.

**CI-based deploy, not local `wrangler dev`.** Building the Container image locally on this repo's Apple Silicon development host crashes deterministically (`uv__io_poll: errno == EEXIST`, a libuv/Colima-VZ interaction under the QEMU/HVF investigation this Agent Note does not resolve) regardless of Colima VM backend, memory, or Docker Desktop as an alternative. `.github/workflows/deploy-cloudflare-worker.yml` (`workflow_dispatch` only) builds and deploys from a GitHub-hosted Linux runner instead, which has no such VM layer. `wrangler deploy --containers-rollout=immediate` is required on every deploy: the default gradual rollout leaves a recently-connected instance on its old image until it passes a grace period, and every verification request during this deployment's own bring-up kept resetting that grace window — a single-Workspace deployment has no multi-instance population to stage a gradual rollout across, so immediate replacement is the correct behavior here, not a risk being traded away.

## Alternatives considered

**Two packages (`cloudflare-host-container` / `cloudflare-edge-gateway`) instead of one.** Both halves are compiled and deployed together by the same `wrangler deploy` regardless of package boundaries, are never independently versioned or consumed by a different caller (the gateway is the Durable Object's only caller), so a split would add cross-package import overhead without a real seam to protect — unlike the storage/session split, where each side has its own independent consumer.

**Wiring the D1 providers and Worker/Container plugins into `dsh-base` or `dsh-web-app` behind a config flag**, instead of a separate opt-in bundle. Rejected: every default profile would carry Cloudflare-specific dependencies (`@cloudflare/containers`, `wrangler` types) it never uses, and would need a flag to turn behavior off rather than simply not mounting it — this repo's "no hardcoded tunables in plugins" rule.

**One Container per Session instead of per Workspace.** Rejected: Sessions in a Workspace need to see each other's files today (one Session's edit is visible to another opened later in the same Workspace); per-Session containers would silently break that.

**A distributed lock for `dsh-credentials-d1`'s `modifyRecord`**, instead of accepting last-write-wins. D1's REST API exposes no transaction primitive that would let a read-decide-write sequence hold exclusion across the decision step; `dsh-session-persistence-d1` already accepts the same trade-off for its own read-then-batch-write sequence, and building a lock this API cannot actually guarantee would be worse than documenting the real limitation.

**`resolve()`/`describe()` env-fallback direction for `dsh-credentials-d1`: `process.env` as a bootstrap default under a D1 override, not `dsh-credentials-local`'s "inherited environment wins."** The roles are reversed from a local deployment: here `process.env` is a fixed deploy-time value (the container's forwarded `DEEPSEEK_API_KEY`/`ANTHROPIC_API_KEY`), while D1 is the Settings-UI-writable store a caller expects to actually take effect.

## Consequences

A deployment lives at a `workers.dev` subdomain or custom domain, gated by Cloudflare Access sign-in, with the default model set to Claude Haiku 4.5 via a directly composed `llm-pi-ai` `anthropic` route (bypassing the ephemeral-disk-backed Settings-page path this deployment cannot use for a durable default). Cloudflare Containers is beta with no SLA and an API that can change without notice; the container-orchestration code in `packages/cloudflare/cloudflare-worker` is the most likely place in this change to need follow-up work as that API moves. Cold start from idle takes on the order of a minute for this repository's full Cordis composition (~1000 workspace packages), surfaced as an explicit `{"status":"starting"}` rather than hidden latency; `sleepAfter` is `'30m'`, untuned against real usage. D1 is the durability floor: a D1 outage or throttling makes Workspaces unreadable even though Containers may be healthy, an accepted dependency with no in-repo mitigation beyond surfacing D1 failures as explicit errors. `dsh-credentials-d1`'s `modifyRecord` is last-write-wins under concurrent callers, documented in its README rather than assumed away. No Miniflare Container test coverage exists (`cloudflare/workers-sdk#10408`, an upstream bug): `packages/cloudflare/cloudflare-worker`'s own integration tests run everything up to the point the Container would actually start, and this deployment's live behavior beyond that boundary is verified only by the real, deployed instance, not by CI.

## Testing

`packages/cloudflare/cloudflare-worker/tests/gateway.workers.spec.ts` runs under `@cloudflare/vitest-pool-workers` against the real Workers runtime (Miniflare's D1/Durable Object emulation, no live Cloudflare account): unauthenticated rejection without touching D1, 404 on a nonexistent explicit Workspace, 502 on a D1 failure, `DEFAULT_WORKSPACE_ID` skipping the D1 check entirely, and session affinity by Durable Object id. `packages/credentials/credentials-d1/tests/d1-provider.spec.ts` covers every `CredentialProvider` abstract method, the env-fallback precedence, empty-value rejection, and both Cordis events at 100% statement/branch/function/line coverage on `src/**` against a package-local fake D1 REST server. Live verification against the real deployed instance: Workspace creation, Session creation with a real tool call (`ls -la` via the shell tool, Claude Haiku 4.5), and Workspace/Session survival confirmed empirically across dozens of Container replacements and cold restarts during this change's own deployment debugging, all state D1-backed rather than on the Container's ephemeral disk.
