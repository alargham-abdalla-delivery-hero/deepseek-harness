# Agent Note: Composer quick-action row

Status: implemented

English | [中文](2026-08-20-composer-quick-actions.zh.md)

## Problem

The composer has no fast path into common domain workflows (pulling a lead-generation list, an income statement, a balance sheet); a user types the full request from scratch every time. Nothing under the composer offers a one-click shortcut, and no plugin other than the one owning a dock entry can add buttons to it.

## Decision

A new client-only package, `packages/client/ui-quick-actions/` (`@deepseek-ai/dsh-client-ui-quick-actions`), follows the `ui-input-trigger`/`ui-commands` split: an empty host `apply()` so the plugin still appears in `cordis.yml`/Loader, and the real behavior in `src/client/`.

`QuickActionsService` (`ctx.quickActions`) is a flat, in-memory registry of `{ id, label, insertText, overflow?, order }` entries. `register(entry)` throws on a duplicate id and returns a disposer (the registration-as-effect convention); the service derives a `{ visible, overflow }` split by ascending `order` on every register/dispose and republishes it through a `SnapshotStore`. The plugin seeds eight default entries at `apply()` through that same `register` call — four visible (Lead generation, Income Statements, Balance sheet, Cash Flow Statement) and four overflow-only (Market Research, Competitor Analysis, Financial Forecast, Investor Pitch) — so another plugin adds entries the identical way — no edit to this package.

`QuickActionsRow` registers into `conversation.composer.dock` (`packages/client/ui-conversation`'s existing `kind: 'list'` seat for the band under the composer card, inside the bar's width column) at `order: -10` — ahead of the shipped `StatsLine` entry (`order: 0`), so the row sits directly under the composer and the ambient stats text trails below it. Its CSS matches the composer card's own width rule (`width: 100%; max-width: var(--dsh-composer-card-max-width)`, no further inset) rather than subtracting the dock inset a second time, since the footer already sits inside `InputBar`'s side-clearance-padded root — that double subtraction previously left the row inset from the card's own left/right borders instead of flush with them.

The row is a responsive "priority+" toolbar: `overflow`-flagged registry entries always land in the "More" menu, while `visible`-flagged entries render as buttons up to however many the exported pure function `fitVisibleCount` (widths, available width, pinned-overflow count) says fit — reserving room for "More" whenever any later visible entry or a pinned entry could still spill, so a full fit reserves nothing and "More" itself is omitted. A `useLayoutEffect` measures every visible entry's natural width plus a same-styled "More" button off-screen (`.measure`, `aria-hidden`) before paint, so there is no flash of the wrong buttons, and a `ResizeObserver` on the row re-measures on every resize (`packages/client/ui-layout/src/client/AppFrame.tsx`'s ResizeObserver-container-tracking precedent; no existing component in the repo already did this exact fit-and-overflow computation). Reusing the `Menu` primitive (`side="right"`, `getAnchorRect` on the button ref) covers the dropdown itself rather than a bespoke popover. Selecting any entry — a row button or a menu item — calls `inputActions.setDraft(insertText)` (the same face `/` commands and file-mention insertion use) and never submits, so the user can edit before sending. Every control disables while `input.phase` is `'adjudicating'` or `'submitting'`, mirroring `InputBar`'s own busy gate; the row never subscribes to session/input directly, only reads the owner-share snapshot the `.dock` seat already re-renders on.

The plugin is wired into the web client's default composition (`packages/bundle/web-app/cordis.patch.yml`, `packages/bundle/web-app/package.json`) and the client-plugin aggregate (`tsconfig.client.json`, `tsconfig.base.json`), so `pnpm dsh web` mounts it without an opt-in flag; the assembled-jsdom test harness (`apps/web/tests/assembled-boot.ts`) needs no matching addition because it auto-discovers boot entries from the same bundle patches and each package's own `dsh.client` declaration.

`conversation.composer.dock`'s footer previously rendered only outside hero (blank-session) posture, on the assumption that its one registrant, `StatsLine`, has nothing to show before a turn exists. `packages/client/ui-conversation/src/client/skeleton/ConversationRoot.tsx` now renders that footer whenever the owner `zone` is defined, hero or not, because the seat now has a second registrant whose whole purpose is to help a user start a session — hiding it exactly when the composer is blank defeats the request. `StatsLine` keeps its own `groups.length === 0` guard, so its rendered behavior in hero is unchanged; only the seat-level gate moved down into each registrant's own logic. The `conversation.composer.dock` JSDoc in `packages/client/ui-conversation/src/client/contract/slots.ts` documents the seat as open to controls the composer's own turn acts on, not only ambient readouts.

## Alternatives considered

- **Hardcode the three buttons directly in `ui-conversation`, no registry** — rejected: every other `.dock`/`.overlay` contributor in this repo ships as its own plugin rather than growing the declaring package, and a fixed set with no extension point contradicts the request that other plugins be able to add entries without editing this one.
- **A bespoke dropdown/popover for "More"** — rejected: `Menu` already implements the exact side-anchored, keyboard/focus/dismiss-consistent interaction (the same primitive backing the slash-command menu and the workspace picker); a new component would duplicate that behavior for no gain.
- **Submit immediately on click** — rejected: matches neither `/` commands nor file-mention insertion, both of which write the draft and let the user review; an unreviewed immediate submission also risks an accidental send from a stray extra click.
- **Register into `conversation.input.left`/`.right` instead of a dock seat** — rejected: those seats share a one-row height budget with resident composer chrome and are documented for a single small always-visible control, not a labeled multi-button row; a dock seat is for content that wants its own line.
- **Register into `conversation.input.dock` (above the composer, alongside Todo/Goal/Queue) instead of `conversation.composer.dock`** — rejected: a banner above the whole input area reads as competing chrome rather than a composer-adjacent action strip; `conversation.composer.dock` sits inside the same width column directly under the card, which matches a set of buttons meant to act on what the user is about to type.
- **Keep the seat's hero gate and hide the row on the blank screen** — rejected: the blank/hero screen is exactly where a one-click shortcut into a domain workflow matters most; hiding it there for the sake of preserving `StatsLine`'s original assumption would defeat the feature's purpose.
- **Keep the static visible/overflow split, "More" always rendered** — rejected: a fixed split does not adapt to viewport or sidebar width, so a narrower window either clips buttons or wraps the row to a second line; measuring the real row width and moving only what does not fit into "More" — which then also disappears once everything fits — matches how a person actually reads "no room left" as the trigger for an overflow menu.

## Consequences

Other plugins can contribute quick actions with one `ctx.quickActions.register(...)` call and no dependency on this package beyond the declared service face. The trade-off: the eight shipped default entries are fixed English strings with no `cordis.yml` `Config` surface, and "More" always opens `side="right"` regardless of text direction — both documented under this package's `README.md` `## Known Limitations and Deferred Work`, deferred until a real second consumer needs different defaults or right-to-left placement. The responsive measurement has no real layout engine in jsdom, so every automated test mocks `getBoundingClientRect`/`clientWidth` directly (see Testing below) rather than exercising real layout; the actual pixel-fit and live-resize behavior was manually verified against a real Chromium build during implementation, not by an automated, CI-running check.

## Testing

`packages/client/ui-quick-actions/tests/service.client.spec.ts` covers `QuickActionsService` register/duplicate-id/dispose and the visible/overflow ordering, including the HMR-safety shape (dispose of the registering fiber removes the entry). `tests/apply.client.spec.ts` covers the real `apply()` wiring on a cordis `Context` + `SlotRegistry` (default-entry seeding, dock registration at `order: -10`, per-session scope resolution failing loud on an unknown session, fiber teardown). `tests/quick-actions-row.client.spec.tsx` covers `fitVisibleCount` directly (full fit reserving nothing, a reservation that spills the tail, a pinned entry keeping the reservation even once every visible entry would otherwise fit, and the always-at-least-one fallback) plus `QuickActionsRow` itself (props-direct, the `QueueDock`/`GoalDock` precedent), mocking `getBoundingClientRect` per button label and `clientWidth` on the row (the `AppFrame` `ResizeObserver`-stub convention) to assert: every entry renders directly with no "More" when the row has room and nothing is pinned; "More" renders for a pinned entry even when every visible entry fits; a too-narrow row spills its tail into "More" alongside any pinned entry; a live resize recomputes the cutoff; a click writes the draft through `inputActions.setDraft`; and every control disables during the busy input phases. `tests/apply.client.spec.ts` covers the real `apply()` wiring on a cordis `Context` + `SlotRegistry` (default-entry seeding — four visible, four pinned-overflow — dock registration at `order: -10`, per-session scope resolution failing loud on an unknown session, fiber teardown). `apps/web/tests/quick-actions-row.snapshot.ts` is a keyless assembled-jsdom snapshot over the real built client bundles, discovered automatically by `apps/web/tests/assembled-boot.ts` from the same bundle patches and package declarations `dsh web` reads; it mocks a generously wide row (jsdom has no layout engine) to pin the default row's visible button labels and prove both a row-button click and a "More" menu-item click fill the composer draft.
