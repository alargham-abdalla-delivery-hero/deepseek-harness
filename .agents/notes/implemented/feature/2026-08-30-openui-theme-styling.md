# Agent Note: OpenUI renderer components styled against dsh-client-ui-theme tokens

Status: implemented

## Problem

`dsh-client-ui-openui`'s components (`Card`, `Table`, `BarChart`, `PieChart`, `List`/`ListItem`, `Heading`, `Text`, `Stack`) rendered plain unstyled semantic HTML/SVG, as the package's own README documented under "Minimal styling." Compared side-by-side against the reference [OpenUI](https://github.com/thesysdev/openui) playground rendering the same OpenUI Lang source, the harness's rendering read as visually broken: no section dividers, an unbordered table with no header/row distinction, a rainbow multi-hue bar chart with per-bar value text and no axis, a solid (non-donut) pie with no side legend layout, and bare `<li>` bullets. Once restyled, a second gap surfaced the same way: the reference's charts respond to the mouse (hover highlights, a value readout, clickable/focusable data points) while `BarChart` and `PieChart` were static SVG with no event handlers at all.

## Decision

Each component now imports a colocated CSS Module (`Foo.module.css`, following the repository-wide `packages/client/ui-*` convention — no Tailwind, no CSS-in-JS) that references `dsh-client-ui-theme`'s existing CSS custom properties (`--dsw-alias-bg-*`, `--dsw-alias-label-*`, `--dsw-alias-border-l1..l4`, `--dsw-alias-state-*`, `--dsw-font-markdown-*`), the same tokens `packages/client/ui-primitives/src/markdown/MarkdownText.module.css` uses for the chat's own markdown rendering. This keeps the dashboard visually consistent with the rest of the product and in both light/dark themes (the tokens already carry `body[data-ds-dark-theme]` overrides) without adding a runtime dependency.

Specific choices:
- `Stack` puts a `border-bottom` divider under every child except the last, keyed off the `data-openui-component` attribute every curated component already carries (an attribute selector passes through CSS Modules unhashed).
- `Card`'s title renders larger (`--dsw-font-markdown-h2`) with no bordered box — visually a section header + divider, matching the reference (which does not box each `Card`; only `Table` gets a border).
- `Table` gains a bordered/scrollable wrapper, a muted header row, and per-row dividers matching `MarkdownText.module.css`'s own table styling (`border-l3` under the head, `border-l2` between rows, `10px 16px` cell padding). A cell matching `/^[+-]\d/` (a signed delta like `+38%`) renders as a colored pill (`--dsw-alias-state-success-*` / `--dsw-alias-interactive-bg-hover-danger` + `--dsw-alias-state-error-secondary`) — a text-pattern rule, not a column-name lookup, so it applies to any table regardless of header text.
- `BarChart` draws "nice" axis gridlines/tick labels (a small 1/2/5×10ⁿ step algorithm, no charting dependency) and renders every bar in one accent color (`--dsw-alias-state-business-primary`) instead of a per-index rainbow, since `ChartDatum` carries no series-color field — one BarChart call is one series. Per-bar value text is dropped in favor of the axis (matching the reference); the category label under each bar stays.
- `PieChart` draws a donut (annular sector paths, `INNER_RADIUS`/`OUTER_RADIUS`) instead of a solid pie, keeps a still-adjacent-category palette (`chartColor()`, now sourced from theme tokens instead of literal hex) for the ring, and renders the legend beside the chart. The legend's "label: value" text stays a single text run inside one `<span>` (not split into separate label/value spans) — `dom-testing-library`'s default `getByText` matcher joins only an element's *direct* text-node children, not full recursive `textContent`, so splitting the string across sibling elements would make no single element match the existing `renders a PieChart with a title and one slice per data point` test's `getByText('A: 30')` assertion.
- `chartColor()`'s fixed-hex return values changed to `var(--dsw-alias-state-business-primary)` / `var(--dsw-static-deepseek-*)` token references; `chart-colors.client.spec.ts`'s literal-equality assertions were updated to the new token strings in the same change (same wrap-around/negative-index-fallback behavior, new values).
- `ListItem` gained a leading bullet marker only — its schema has one `text` prop (no icon/subtitle field), so a reference render showing a per-issue icon and caption line reflects data this renderer's vocabulary does not carry; fabricating icon selection from keyword-matching item text would be a hardcoded, non-generalizing heuristic, so it was left out. The README's Known Limitations section now states this explicitly.
- `BarChart` and `PieChart` are interactive purely client-side (`useState` in each component; no `Query()`/`Mutation()`/tool round-trip, staying inside the v1 non-goal the original design note draws). Each data point (a `<rect>`, an annular `<path>`, and its `PieChart` legend `<li>`) is a `role="button"` with `tabIndex={0}`, responds to hover, focus, and `Enter`/`Space` identically to a click, and tracks two independent states: `hovered` (transient, clears on mouse-leave/blur) and `pinned` (toggles on click/activation, survives the pointer leaving — the touch- and keyboard-accessible equivalent of "hover"). The active point (`pinned ?? hovered`) drives three effects: a `"label: value"` readout next to the chart title (`BarChart`), a brightened/dimmed slice plus its matching legend row (`PieChart`, cross-highlighting in both directions since both share the same `active` state), and `aria-pressed`/`aria-label` for assistive tech. `Table` rows and `ListItem`s get a pure-CSS `:hover` background tint — no state needed since they carry no extra per-row data to reveal.
- Neither chart's native SVG `<title>` (a real browser tooltip) survived: the `BarChart` readout and the `PieChart` legend already show the exact same `"label: value"` string once a point is active, and `dom-testing-library`'s default `getByText` only matches an element whose own direct text-node children join into the full search string — a `<title>` child with identical text made two elements match, throwing "Found multiple elements" in `render-element.client.spec.tsx`. Dropped in favor of the always-visible on-chart readout/legend, which does not have this collision.
- `PieChart`'s `.svg` had a stray fixed `180×180px` box while every sibling component (`Table`'s wrapper, `BarChart`'s `width: 100%` SVG, `Card`'s section) fills its parent's width — at a typical chat card width the donut rendered visibly smaller than the bar chart next to it. Changed to `width: min(100%, 260px); aspect-ratio: 1; height: auto;`: it now scales the same way the others do (shrinks on a narrow container instead of overflowing) but caps at a size that reads as comparable to the rest of the dashboard instead of a small fixed icon. No viewBox/geometry constants changed — SVG scales its existing `0 0 180 180` content to fill whatever CSS box it's given.

## Alternatives considered

**Depend on `@openuidev/react-ui`** (Thesys's prebuilt component kit) instead of hand-rolled CSS. Rejected: [the original design note](2026-08-23-openui-generative-ui-rendering.md) (Decision 5) already ruled this out for v1 — a second unreviewed third-party component implementation on a model-influenced rendering surface is a larger security review than this styling gap justifies, and the harness already owns a theme token set that produces a comparable look.

**Detect `ListItem` icons from keyword-matching the item's text** (e.g., "CPU" → a chip icon, "Database" → a database icon) to match the reference's per-issue icons. Rejected: this only generalizes to the one example dashboard used for comparison; the schema has no icon field, and inventing icon selection from prose is exactly the kind of hardcoded, non-evidenced heuristic the repository's package conventions warn against.

**Split the `PieChart` legend's label and value into separate styled spans** for independent alignment (label left, value right). Rejected once it broke `getByText('A: 30')`-style assertions in `render-element.client.spec.tsx`: `dom-testing-library`'s default text matcher does not recurse into child elements, so two sibling spans have no single element whose own text equals the full `"label: value"` string. Kept as one `<span>` with both interpolations, at the cost of losing independent right-alignment for the value column.

**A floating tooltip that follows the cursor**, positioned via `getBoundingClientRect`/`onMouseMove` math, to match the reference more literally. Rejected: `BarChart`/`PieChart` render as an inline `viewBox`-scaled SVG (`width: 100%`), so a tooltip's on-screen position depends on the container's actual rendered size, not the fixed SVG user-space coordinates the rest of the chart geometry uses — correct math would need a `ResizeObserver` and a ref, for a payoff (a tooltip that tracks the mouse instead of sitting in a fixed spot) this dashboard's small, fixed-size datasets don't need. The always-visible readout/legend-highlight (this Decision) gives the same information with none of that complexity.

**Pan/zoom or drag-to-reorder on the charts.** Not implemented: nothing in `dsh-openui-lang`'s fixed-size `ChartDatum[]` data benefits from panning or zooming, and there is no reactive layer (Non-Goal, upstream design note) to persist a dragged order back to a model turn. "Interactive" here means hover/focus/click feedback on existing data, not manipulating the chart's own layout.

## Consequences

The chat client's `render_ui` dashboards now read like the rest of the product (theme-token colors, dividers, a bordered/scrollable table, an axis'd bar chart, a donut pie with a legend) instead of unstyled browser-default HTML, and its two charts respond to hover, keyboard focus, and click the way the reference's do. Cost: `ListItem` still cannot show a subtitle or icon, and `BarChart` shows no legend swatch (no series-name field exists to label it) — both are schema gaps in `dsh-openui-lang`, not renderer gaps, and would need a `dsh-openui-lang` schema change (out of scope here) to close. There is no cursor-following tooltip and no pan/zoom (Alternatives considered). The `.zh.md`/`.i18n.yaml` counterparts for this Agent Note and the touched README still need `dsh-translate-docs` run before this change can pass `doc-sync`.
